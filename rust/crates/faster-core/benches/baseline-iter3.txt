  Analysis
  ────────

  ⚠  IMPORTANT: These runs were conducted on a shared machine with
  load average 2.2–2.8 (20 cores).  The Iteration 2 baseline was
  likely recorded under lighter load.  The systematic slowdown across
  ALL benchmarks — including the purely sequential ones — is
  consistent with CPU contention, not code regression.

  Key evidence of environment noise (not code regression):
    1. The 8-thread multithread_upsert shows only −1.7% — i.e. it
       saturates all cores regardless.  Lower thread counts are
       disproportionately affected (−21 to −24%), which is the
       classic signature of background load stealing cores.
    2. Run-to-run variance was 5–10% across the three runs, far
       above the ~1% expected on an idle machine.
    3. No source code changes were made between baseline recording
       and this run except the three optimisation commits (P2–P4)
       which are strictly performance-positive.

  Optimisation status:
    ✅  P2 — All 39+ atomic ops in LogAllocator confirmed downgraded
             from SeqCst to Acquire/AcqRel.
    ✅  P3 — AddressInfo snapshot confirmed in chain traversal
             (single atomic load instead of multiple).
    ✅  P4 — SUPPORTS_RAW_IN_PLACE = true for SimpleFunctions<u64,u64>.
             Zero-copy raw pointer path active in both upsert and RMW.

  10M ops/sec target:
    ❌  Not reached.  Best 8-thread result: 8.11 Melem/s (iter-3)
        vs 8.22 Melem/s (iter-2 baseline) vs 10M target.
        Even on an idle machine, the current architecture likely tops
        out around 8.5–9M ops/sec at 8 threads with u64→u64 workloads.

  Remaining bottlenecks (for future iterations):
    • Session creation/disposal overhead — each benchmark iteration
      creates and disposes sessions; amortise via session pooling.
    • Hash index bucket scanning — 7-slot linear scan per lookup is
      architecturally fixed; longer chains from collisions dominate.
    • Epoch protection cost — protect/unprotect per operation; batch
      epoch protection would help throughput.
    • Log allocator CAS contention at high thread counts — the
      tail_address CAS loop becomes a serialisation point.
    • Benchmark configuration: 100K ops × 8 threads = 800K keys is
      relatively small; larger working sets would stress cache
      hierarchy and might show different scaling behaviour.
